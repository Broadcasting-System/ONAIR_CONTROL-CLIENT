# ADR: 컨트롤·송출 화면 저장소를 합치지 않는다 (2026-10-26)

- 상태: **결정 — A안(합치지 않고, 복사본이 어긋나면 CI 가 실패)**
- 범위: `Broadcasting-System/ONAIR_CONTROL-CLIENT`(Next 15 + 데스크톱 앱 `desktop/`, Tauri 2), `Broadcasting-System/ONAIR_DISPLAY-CLIENT`(Next 16).
  서버(`ONAIR-SERVER`, Python FastAPI)는 언어·패키지 관리·배포가 달라 처음부터 대상이 아니다(공유하는 것은 API JSON 모양뿐 — 필요하면 OpenAPI 타입 생성).

## 배경

재연결 훅·Sentry 설정·테스트 도구를 두 저장소에 같은 코드로 복사해 두었다(PR CONTROL #7·#10, DISPLAY #2·#3).
복사본은 한쪽만 고치고 끝나기 쉽다. pnpm 모노레포로 합칠지 검토했다.

## 측정 (2026-10-26, origin/main + 열린 PR 브랜치)

| 종류 | 내용 | 규모(한쪽 기준) |

| **합계** | | **약 700~750줄 — 프론트 전체(컨트롤 약 4.6만 줄 + 송출 화면 약 4.6천 줄)의 2% 미만** |

- 복붙 탐지(`npx jscpd@4 control display --min-lines 6 --min-tokens 50`, 두 저장소의 스타일 차이 — 세미콜론·따옴표 — 를 맞춘 뒤):
  글자 그대로 같은 블록 **135줄**. 나머지는 '같은 규칙, 다른 코드'라 도구로는 안 잡힌다.
- 열린 PR 8개(CONTROL #6~#10, DISPLAY #1~#3)는 쌍마다 머지 충돌이 없다(`git merge-tree`).

## 선택지

| | 내용 | 비용 | 위험 |
|---|---|---|---|
| **A. 합치지 않음 + 복사본 검사** | 같은 코드로 두는 파일 목록을 두 저장소에 두고, CI 가 다른 저장소 main 과 비교해 어긋나면 실패 | 1~2시간 | 거의 없음. 같은 규칙 다른 코드(C줄)는 여전히 사람이 맞춰야 함 |
| B. pnpm 모노레포 전체 | 새 저장소에 히스토리 보존 이전(`git filter-repo --to-subdirectory-filter` + `merge --allow-unrelated-histories`), `packages/shared`, CI 재구성, 학교 서버 스크립트 수정·전환 | 개발 2.5~3.5일 + 학교 서버 전환 1시간 | 학교 서버 업데이트·시작 스크립트(폴더 이름·포트를 직접 적음)가 바뀜 — 실수하면 학교 업데이트가 멈춤. Tauri iOS·Android 빌드(상대 경로) 재확인, 저장소 Secrets·Actions 재등록 |
| C. 그림자 모노레포 | B 를 새 저장소에서만 하고 학교 서버는 옛 저장소 유지, 전환은 나중 | 개발 2~2.5일 | 학교 위험 없음. 대신 전환 전까지 진실이 두 곳(동결·동기화 필요) |

도구: 하게 되면 pnpm workspace 단독. 앱 2개 + 패키지 1개라 Turborepo(캐시·작업 그래프)·Nx 는 얻는 것보다 설명할 것이 많다.

## 결정과 이유 — A

1. **문제가 작다.** 공유할 코드가 2% 미만. 개발자 1명, 저장소 2개라 두 PR 을 같이 내는 비용이 낮다.
2. **위험이 이득보다 크다.** 학교가 매일 쓰는 배포 경로(서버 PC 의 `ONAIR 업데이트.cmd`·`ONAIR 시작.cmd`)를 바꿔야 하고,
   이득은 코드 정리뿐이다.
3. **진짜 위험은 '어긋남'이다.** 그건 CI 검사로 막을 수 있다 — 아래.

## A 의 구현

- `scripts/shared-copies.json`: 같은 코드로 두는 파일 쌍 10개(위 9개 + 검사 스크립트 자신·목록), 일부러 다른 파일 3개와 이유.
- `scripts/check-shared-copies.mjs`: TypeScript 스캐너로 토큰을 나눠 비교. 주석·공백·줄바꿈·세미콜론·따옴표 종류·끝 쉼표는
  저장소마다 스타일이 달라 빼고, 이름·연산자·문자열 값·숫자가 같아야 같다. 다르면 파일과 처음 갈라지는 곳을 찍고 실패.
  한쪽에만 있는 파일은 알리기만 한다(한쪽 PR 이 먼저 들어간 사이) — `--strict` 면 실패.
- CI(`.github/workflows/test.yml`): 다른 저장소 main 을 받아(두 저장소 모두 공개라 토큰 불필요) 비교.
- 시험: `src/test/sharedCopies.test.ts`(컨트롤) — 스타일만 다르면 통과, 값이 다르면 실패, 템플릿 문자열 안, `--strict`.
- 처음 돌렸을 때 바로 어긋남 1건을 잡았다: `test/setup.ts` 에 ResizeObserver 대역을 컨트롤(#9)에만 넣었다 → 송출 화면에도 넣음.

열린 PR 이 모두 들어가면 CI 에 `--strict` 를 붙인다(한쪽에만 있는 파일도 실패).

## 다시 검토할 조건 (하나라도 맞으면 B·C 를 다시 본다)

- 같은 코드·같은 규칙 코드가 **2,000줄 이상** 또는 공유 파일 쌍이 **20개 이상**
- 앱이 **3개 이상**(예: 선생님 앱·live 를 따로 떼거나 새 화면 앱)
- 개발자 **2명 이상**이 두 저장소를 같이 고침 — 두 PR 맞추기 비용이 커짐
- 복사본 검사가 한 달에 **3번 이상** 실패 — 어긋남이 자주 생긴다는 뜻
- 공유 UI 컴포넌트(디자인 시스템)를 두 앱이 함께 쓰게 될 때
- 학교 서버 배포를 스크립트가 아니라 빌드 산출물(아티팩트) 배포로 바꿀 때 — 전환 위험이 작아짐

그때도 학교 서버 전환은 C 처럼 따로, 시보 시각을 피해 방과 후에 사람과 함께 한다.
